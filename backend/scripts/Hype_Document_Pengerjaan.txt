F-01 · WALLET MOVEMENT MONITOR
Sistem Pemantau Pergerakan Wallet Whale
Tujuan Fitur
Mengapa Diperlukan
 Seluruh sistem bergantung pada deteksi pergerakan 2 wallet whale (Whale A & Whale B) sebagai sinyal awal.
 Tanpa pemantauan real-time, sistem tidak akan tahu kapan whale melakukan swap, transfer, atau perubahan LP.
 Pemantauan harus 24/7 karena pasar meme coin aktif kapan saja, termasuk dini hari.
Siapa yang Menggunakan
 Sistem internal (Layer 0) — tidak ada interaksi manual dari pengguna.
 Developer memantau status koneksi WebSocket lewat dashboard.
Gambaran Fitur
Fitur ini adalah fondasi dari seluruh sistem. WebSocket connection dibuka ke blockchain RPC/Indexer dan
melakukan subscription ke aktivitas on-chain dari dua wallet target. Setiap event yang masuk (swap,
transfer, LP change) direkam dengan timestamp dan diteruskan ke lapisan berikutnya. Koneksi dijaga
tetap aktif dengan mekanisme heartbeat/ping, dan jika terputus akan otomatis reconnect.

Estimasi nilai transaksi dalam USD

timestamp_utc

Waktu event terjadi di blockchain
Alur Bisnis
1
Inisialisasi Koneksi
Saat sistem startup, buka WebSocket ke RPC provider dan subscribe ke wallet Whale A & B.
2
Dengarkan Event
Sistem idle mendengarkan event on-chain secara real-time (logsSubscribe / accountSubscribe).
3
Event Masuk
Setiap transaksi dari wallet target masuk sebagai raw event dengan signature, instruction type, token mint,
jumlah.

Reconnect Otomatis

Skenario Penggunaan
Skenario 1 — Whale A Melakukan Swap
Tujuan: Mendeteksi aktivitas trading whale secara real-time.
Langkah: Whale A swap 10 SOL ke token XYZ. RPC node menerima transaksi → event masuk ke sistem →
diteruskan ke F-02.
Hasil: Sistem meneruskan event ke filter. Jika relevan, trigger engine mulai memantau window 5 menit.
Skenario 2 — Koneksi RPC Terputus Saat Posisi Terbuka
Tujuan: Memastikan monitoring tidak berhenti walau koneksi putus.
Langkah: RPC primary timeout. Sistem gagal ping → deteksi koneksi putus → exponential backoff retry → setelah
3x gagal, switch ke RPC secondary.
Hasil: Monitoring posisi tetap berjalan via RPC secondary. Notifikasi switchover muncul di dashboard.

Alur bisnis:
1. Startup: baca watchlist_wallets dari database, buka koneksi WS ke RPC primary
2. Subscribe ke setiap wallet address di watchlist
3. Loop: terima event → parse → validasi signature unik → kirim ke queue F-02

- Wallet address harus valid Solana pubkey format (base58, 32-44 chars)
- Event signature harus unik (dedup dalam memory window 60 detik)

- Hanya proses event dari wallet yang ada di watchlist aktif (active=TRUE)

melalui F-18.
Kondisi gagal:
- RPC tidak tersedia saat startup: retry 3x, kemudian fallback ke RPC secondary
- Event tidak bisa di-parse: log ke error_log dengan raw data, skip event, lanjut
- Queue F-02 penuh: implementasi backpressure, slow down ingestion
Integrasi:
- Input: watchlist_wallets dari database (F-12 untuk dynamic discovery)
- Output: event stream ke F-02 (Rule-Based Filter)
- Koneksi: F-15 (RPC Fallback) jika primary gagal

F-02 · RULE-BASED RELEVANCE FILTER
Filter Relevansi Berbasis Aturan
Tujuan Fitur
Masalah yang Diselesaikan
 Tidak semua pergerakan wallet adalah sinyal trading. Transfer gas, pindah ke wallet sendiri, atau top-up exchange
bukan sinyal yang relevan.
 Jika event tidak relevan ikut masuk ke trigger window, dataset training akan tercemar dengan false signal.
 Filter ini adalah 'pintu masuk pertama' — memastikan hanya event bermakna secara trading yang diproses lebih
jauh.
Gambaran Fitur
Setiap event dari F-01 divalidasi berdasarkan aturan: apakah transaksi ini melalui DEX router yang
dikenal? Apakah nilainya di atas threshold minimum? Apakah bukan transfer ke wallet sendiri atau
custodial exchange? Apakah bukan sekadar top-up gas (SOL transfer kecil)? Event yang lolos diteruskan
ke Trigger Engine (F-03). Yang gagal di-log sebagai 'irrelevant' untuk audit namun tidak masuk training.
Aturan Filter (Rule Set)
Aturan
Kondisi LOLOS
Kondisi GAGAL
DEX Router Check
Interaksi dengan alamat router DEX publik yang dikenal (Raydium, Orca, pump.fun, dll)
Transfer langsung wallet-ke-wallet tanpa DEX router
Value Threshold
Nilai transaksi > threshold minimum (dikonfigurasi di config.yaml)
Transaksi nilai sangat kecil (top-up gas, dust)
Self-Transfer Check
Pengirim dan penerima adalah wallet berbeda (bukan wallet sendiri)
Transfer ke wallet sendiri / rebalancing internal
Exchange Address
Bukan transfer ke custodial exchange (Binance, Coinbase hot wallet)
Top-up ke centralized exchange
LP Change
LP add/remove yang signifikan
Perubahan LP trivial di bawah threshold
Alur Bisnis
1
Terima Event
Menerima event dari F-01 melalui internal queue.
2
Cek DEX Router
Bandingkan instruction accounts dengan daftar DEX router yang dikenal. Jika tidak cocok → log
'irrelevant_non_dex', skip.
3
Cek Value Threshold
Hitung estimasi nilai USD. Jika di bawah threshold config → log 'irrelevant_low_value', skip.
4
Cek Self-Transfer
Verifikasi penerima bukan wallet sendiri dari watchlist. Jika ya → log 'irrelevant_self_transfer', skip.
5
Cek Exchange Address
Verifikasi penerima bukan alamat custodial exchange yang dikenal. Jika ya → skip.

F-03 · WALLET MOVEMENT TRIGGER ENGINE
Mesin Pemicu Berbasis Window Waktu
Tujuan Fitur
Konsep Kunci
 Mode AND: sistem baru 'yakin' ada sinyal jika KEDUA whale (A dan B) sama-sama bergerak ke token yang sama
dalam window 5 menit.
 Mode OR: cukup salah satu whale bergerak untuk memicu analisis.
 Window ini mencegah satu aktivitas acak satu whale langsung memicu trade — ada konfirmasi yang diperlukan.
 Mode AND/OR dikonfigurasi di config.yaml dan bisa diubah tanpa menyentuh kode.
Gambaran Fitur
Setelah event lolos filter relevansi (F-02), Trigger Engine membuka 'window observasi' 5 menit. Selama
window ini, sistem mengumpulkan event dari wallet lain. Pada akhir window, sistem mengevaluasi apakah
kondisi trigger terpenuhi (AND/OR). Jika ya, system 'fire event' dan mengirim sinyal ke pipeline ML (F-04).
Jika tidak, window di-reset dan monitoring dilanjutkan.
Alur Bisnis
1
Terima Event Relevan
Event relevan masuk dari F-02. Catat token_mint, wallet_source, timestamp.
2
Buka/Perbarui Window
Jika tidak ada window aktif untuk token ini, buka window baru (5 menit countdown). Jika sudah ada,
tambahkan event ke window.
3
Cek Dedup & Cooldown
Sebelum menambahkan, periksa cooldown state (F-14) — jika (wallet, token) masih dalam cooldown, event
diabaikan untuk trigger baru.
4
Evaluasi Kondisi
Mode AND: tunggu sampai window selesai, cek apakah Whale A DAN Whale B sama-sama ada. Mode OR:
langsung fire begitu satu whale muncul.
5
Fire Event
Jika kondisi terpenuhi: buat trigger_event dengan semua metadata, kirim ke F-04 (Feature Extraction).
6
Reset / Lanjut
Jika kondisi tidak terpenuhi: reset window, log sebagai 'trigger_missed', lanjut monitoring.

Tujuan Fitur

Kriteria Retrain
Kapan Retrain Dijalankan
 Jadwal normal: Cron 02:00 UTC setiap hari (volume pasar rendah, minimal gangguan).
 Catch-up: Saat startup, cek timestamp retrain terakhir di model_registry. Jika > 24 jam, langsung retrain.
 Syarat minimum data: 100-150 closed trades, ATAU 50 trades dengan minimal 15-20 berlabel BUY_BENAR.
 Dataset: rolling window 30 hari dari closed_trades. Hanya data real (paper + live), BUKAN mock.
Rollback Guard
Kondisi Rollback Otomatis
 Validation accuracy turun > 5% dibanding model sebelumnya.
 Expectancy(R) berubah dari positif ke negatif: Expectancy = (WR x avg_R_win) - ((1-WR) x 1R).
 Jika rollback: set is_active kembali ke model sebelumnya, tandai model baru sebagai rolled_back=TRUE.
 Notifikasi rollback dikirim ke dashboard sebagai system alert.

Sistem berjalan di laptop biasa — bukan server dengan uptime terjamin. Fitur ini memastikan bahwa saat

PROMPT AGENTIC AI — F-17
Anda adalah Senior Software Engineer. Bangun fitur STATE PERSISTENCE & CRASH RECOVERY (A6).
Tujuan fitur:
Memastikan sistem dapat pulih sepenuhnya dari restart, sleep, atau crash dengan me-restore semua state
kritis ke kondisi terakhir yang valid — terutama posisi trading yang sedang terbuka.
Fungsi utama:
PERSISTENCE (tulis ke disk):

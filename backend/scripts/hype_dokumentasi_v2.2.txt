1.1 Ringkasan Sistem
Aspek
Keterangan
Nama sistem
AI Smart Money Trading System
Tujuan sistem
Mengotomatisasi deteksi sinyal trading meme coin berbasis pergerakan wallet "smart
money" (whale wallet terpilih), memvalidasinya dengan model machine learning dan
pengecekan keamanan token, lalu mengeksekusi entry/exit secara otomatis dengan tiga
lapis proteksi risiko.
Masalah bisnis yang
diselesaikan
Trading meme coin manual membutuhkan reaksi dalam hitungan detik terhadap pergerakan
wallet dan risiko rug pull yang sangat tinggi (mayoritas token meme coin berakhir sebagai
rug pull atau kehilangan likuiditas total) — kecepatan reaksi manusia tidak cukup untuk
menangkap sinyal maupun menghindari kerugian dari rug yang terjadi dalam hitungan detik.
Stakeholder yang terlibat
Operator/pemilik sistem (single-user) sebagai satu-satunya pengguna manusia; secara
tidak langsung, penyedia layanan eksternal (RPC node, pump.fun, DexScreener) sebagai
pihak ketiga yang sistem bergantung padanya.
Target pengguna
Individu yang melakukan trading meme coin di ekosistem Solana/pump.fun dengan modal
terbatas, dijalankan dari laptop pribadi (biasa/gaming) tanpa infrastruktur komputasi tinggi.

Performance

Reliability

(misal RPC putus untuk kill-switch) tidak boleh menghentikan lapis lain (price-based SL tetap aktif).
Maintainability
Threshold dan parameter operasional (confidence threshold, trigger window, tier trailing TP, dsb)
disimpan di satu file konfigurasi terpusat (config.yaml), bukan tersebar di kode, agar kalibrasi ulang
tidak memerlukan redeploy.
Auditability
Setiap posisi closed mencatat exit_reason, confidence_score, dan model_version yang menghasilkan
sinyal — memungkinkan audit retrospektif terhadap kualitas sinyal terpisah dari dampak rug pull
eksternal.
ASUMSI SISTEM
Dokumen sumber tidak menyebutkan target SLA numerik (mis. "sistem harus merespons dalam X ms") maupun
target uptime persentase. Non-functional requirements di atas disusun sebagai prinsip kualitatif yang konsisten
dengan filosofi dokumen sumber ("event-driven, bukan polling"; "hardware terbatas"), bukan angka SLA formal —
angka konkret memerlukan keputusan operator berdasarkan hasil pengujian live.

3.1 Modul Wallet Monitoring
Real-Time Wallet Listener
Aspek
Keterangan
Tujuan
Mendeteksi aktivitas on-chain dari wallet target tanpa delay polling.
Deskripsi
Subscribe ke RPC node via WebSocket (logsSubscribe/accountSubscribe) untuk menangkap swap,

Input
Alamat wallet target (dari watchlist_wallets), koneksi WebSocket RPC aktif.
Output
Event mentah (signature transaksi, instruction type, token mint, jumlah, wallet pengirim/penerima)

Keterangan

3.2 Modul Trigger & ML Pipeline

UC-01 — Deteksi Sinyal dan Eksekusi Entry Otomatis
Aspek
Keterangan
Aktor
Sistem Otomatis (Trigger & ML Pipeline, Eksekusi Otomatis)
Tujuan
Mendeteksi pergerakan wallet target, memvalidasinya melalui ML dan safety check, lalu membuka
posisi secara otomatis jika seluruh syarat terpenuhi.
Pre-condition
Wallet A/B aktif di watchlist; RPC WebSocket terhubung; model aktif tersedia di model_registry;
Position Correlation Cap belum tercapai.
Main Flow
1. Wallet Listener mendeteksi event on-chain dari Whale A/B.
2. Rule-Based Classifier memeriksa relevansi event.
3. Token Age & Liquidity Floor Filter memeriksa kelayakan token.
4. Dedup & Cooldown Check memeriksa apakah pasangan (wallet, token) sedang cooldown.
5. Trigger Window Engine memeriksa kondisi AND/OR terpenuhi.
6. Feature Extraction menyiapkan feature vector.
7. XGBoost Inference Engine menghasilkan direction, confidence, target price.
8. Token Safety Check memvalidasi keamanan token.
9. Confidence Threshold Gate memeriksa confidence ≥ 75% dan safety check lolos.
10. Position Sizing menghitung ukuran posisi dari risk_pct dan jarak SL.
11. Auto-Entry mengirim order beli via pump.fun API.
12. Posisi berstatus OPEN, tiga lapis proteksi diaktifkan.

 Jika confidence < 75% atau safety check gagal, sinyal dicatat sebagai log-only (tidak lanjut ke UC-02) dan tetap masuk

 Jika Position Correlation Cap sudah tercapai, sinyal dicatat namun entry tidak dieksekusi.

 Jika Token Safety Check API timeout, sistem fail-closed — alert diblokir, bukan diloloskan (lihat A3).
 Jika order entry gagal setelah retry maksimal 2x, status dicatat sebagai FAILED_ENTRY, tidak masuk closed_trades.
Post-condition
Posisi baru berstatus OPEN dengan tiga lapis proteksi aktif, ATAU sinyal tercatat sebagai log-only/FAILED_ENTRY

notifikasi darurat untuk kejadian yang memerlukan perhatian segera. Outcome:
operasional menjadi semi-pasif, sistem berjalan mandiri dengan pengawasan periodik.
Retrain otomatis berkelanjutan
Setiap 02:00 UTC, model dilatih ulang dari rolling window 30 hari, dengan rollback
otomatis jika performa menurun. Outcome: model terus beradaptasi terhadap kondisi
pasar terbaru tanpa intervensi manual.
Evaluasi periodik oleh Operator
Operator secara berkala meninjau expectancy(R) jangka panjang dan menyesuaikan
risk_pct_per_trade atau batas Position Correlation Cap sesuai pertumbuhan modal dan
toleransi risiko. Outcome: parameter risiko tetap relevan terhadap kondisi modal
Operator yang berubah dari waktu ke waktu.
Penanganan insiden (crash, RPC
downtime, kill-switch beruntun)
Operator merespons notifikasi darurat sesuai kebutuhan — sistem menangani sebagian
besar skenario secara otomatis (lihat A3, A6, B4), namun Operator tetap menjadi jalur
eskalasi terakhir untuk kondisi yang tidak terselesaikan otomatis (status STUCK).
ASUMSI SISTEM
Dokumen sumber tidak menyebutkan frekuensi atau metode spesifik Operator memantau dashboard (terus-menerus
vs periodik). Journey ini mengasumsikan pola pemantauan semi-pasif yang didukung notifikasi darurat
(Telegram/Discord), konsisten dengan desain sistem yang menghindari kebutuhan intervensi manual per kejadian.
